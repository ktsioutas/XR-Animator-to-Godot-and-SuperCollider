## VMC-to-OSCGroups Bridge Scripts

These Python scripts act as local UDP bridges between **XR Animator** and an **OSCGroups client**.

Default signal route:

```text
XR Animator → 127.0.0.1:39538 → Python bridge
              Python bridge → 127.0.0.1:22244 → OSCGroups
```

The scripts are not OSCGroups clients themselves. They forward packets to the local transmit port of an already running OSCGroups client.

### `vmc_oscgroups_bridge.py`

This is the basic bundle-splitting bridge.

It receives the OSC/VMC packets generated by XR Animator and forwards them to OSCGroups. Small packets are forwarded byte-for-byte without modifying their OSC addresses, bone names, values, or message order.

When an OSC bundle is larger than the configured limit—1,200 bytes by default—the script:

* Recursively extracts the OSC messages contained in the bundle.
* Divides them into smaller, valid OSC bundles.
* Preserves the message order and OSC timetags.
* Ensures that every outgoing packet stays within the configured size limit.

This reduces the risk of IP fragmentation and packet loss when VMC data is transmitted over the Internet through OSCGroups.

Malformed bundles and individual OSC messages that are too large to split safely are dropped with a warning.

### `vmc_oscgroups_bridge_2.py`

This is the extended version of the bridge. It performs the same bundle-splitting and forwarding operations, but it also translates XR Animator’s VRM facial-expression names into ARKit-style names understood by `GodotXRVmcTracker`.

For example:

| XR Animator input      | Additional Godot-compatible output      |
| ---------------------- | --------------------------------------- |
| `blink`                | `EyeBlinkLeft`, `EyeBlinkRight`         |
| `blink_l`              | `EyeBlinkLeft`                          |
| `blink_r`              | `EyeBlinkRight`                         |
| `joy`, `happy`, `fun`  | `MouthSmileLeft`, `MouthSmileRight`     |
| `sorrow`, `sad`        | `MouthFrownLeft`, `MouthFrownRight`     |
| `angry`                | `BrowDownLeft`, `BrowDownRight`         |
| `lookUp`               | `EyeLookUpLeft`, `EyeLookUpRight`       |
| `lookDown`             | `EyeLookDownLeft`, `EyeLookDownRight`   |
| `lookLeft`             | `EyeLookOutLeft`, `EyeLookInRight`      |
| `lookRight`            | `EyeLookInLeft`, `EyeLookOutRight`      |
| `a`, `aa`, `mouthOpen` | `JawOpen`                               |
| `i`, `e`               | `MouthStretchLeft`, `MouthStretchRight` |
| `u`                    | `MouthPucker`                           |
| `o`                    | `MouthFunnel`                           |

Matching is insensitive to capitalization, spaces, underscores, and hyphens.

The original `/VMC/Ext/Blend/Val` messages are always preserved. The bridge only adds translated aliases; it does not replace the original facial data. If an incoming frame already contains a native ARKit-style value, that value takes priority over the generated alias.

Facial values are limited to the valid range `0.0–1.0`. When multiple VRM presets map to the same ARKit channel, the strongest value is used.

The facial translation can be disabled with:

```bash
python3 'vmc_oscgroups_bridge_2.py' --no-face-translation
```

Disabling it makes the extended script operate essentially as a bundle-splitting bridge.

### Running the scripts

Run the basic bridge:

```bash
python3 'vmc_oscgroups_bridge.py'
```

Run the extended bridge with facial translation:

```bash
python3 'vmc_oscgroups_bridge_2.py'
```

Test either script without starting the bridge:

```bash
python3 'vmc_oscgroups_bridge.py' --self-test
python3 'vmc_oscgroups_bridge_2.py' --self-test
```

Available network parameters can be inspected with:

```bash
python3 'vmc_oscgroups_bridge_2.py' --help
```

The main defaults are:

* Input address: `127.0.0.1:39538`
* OSCGroups output address: `127.0.0.1:22244`
* Maximum outgoing OSC packet size: `1200` bytes
* Statistics interval: `5` seconds
* Facial-value logging interval: `2` seconds

Both scripts use only the Python standard library and require no third-party packages.

> **Note:** Facial-name translation makes the messages compatible with the expected Godot naming scheme, but visible animation also requires the avatar mesh to contain the corresponding facial blendshapes or morph targets.
